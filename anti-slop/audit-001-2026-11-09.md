# Anti-Slop Audit 001 — KhepiLabs
Date: 2026-11-09
Mode: AFTER (session override)
Scope: Static source review of the current `main` branch. Reviewed project instructions, core and matching Anti-Slop skills, route/page components, generated home page, admin UI, public/admin stylesheets, document shell, and package scripts. No source files were changed during this audit.

## Findings

### 1. [HIGH] Em dashes remain in shipped UI and metadata
- **Rule:** R-02
- **Evidence:** `index.html` uses an em dash in the document title and Open Graph/Twitter titles. `src/components/generated/KhepiLabsHomePagePreview.tsx` contains an em dash in its hero copy. `src/components/AdminPanel.tsx` also contains em dashes in displayed strings.
- **Why it matters:** R-02 is a Hard Gate rule. The punctuation appears in user-facing content, not only in the Anti-Slop rules or an approved voice sample.
- **Suggested fix:** Replace the em dashes with punctuation that fits each sentence, then scan all shipped copy and metadata for remaining occurrences.

### 2. [HIGH] No documented design direction or Design Read
- **Rule:** R-37
- **Evidence:** The repository has no `DESIGN.md`. The reviewed UI components and styles do not declare the required Design Read or ENERGY / RHYTHM / MOTION dials.
- **Why it matters:** The core requires an explicit direction before design decisions are treated as finished. Without one, the design cannot demonstrate that its energy, section rhythm, and motion are intentional.
- **Suggested fix:** Establish KhepiLabs' actual visual direction in `DESIGN.md` (identity, audience, palette, typography, mood, and the three dials), then use it to review the public and admin surfaces. Do not infer or invent the brand direction during the audit.

### 3. [MEDIUM] Public copy makes unsupported safety and freshness claims
- **Rule:** R-36 (also C-5)
- **Evidence:** The home page hero says downloads are “safe and always updated”. `src/components/PublicPage.tsx` labels a feature “Secure Downloads”. The reviewed source does not provide verification, security checks, or update guarantees supporting those claims.
- **Why it matters:** Security and reliability claims must be real and verifiable. A disclaimer elsewhere does not substantiate a promotional claim.
- **Suggested fix:** Either provide a verifiable basis and define the exact scope of the claim, or replace it with neutral wording describing what the listing actually displays (for example, publisher/source details and version information when supplied).

### 4. [LOW] Iconography defaults to a single generic icon library without a recorded rationale
- **Rule:** R-04 and R-31
- **Evidence:** `src/components/PublicPage.tsx`, `src/components/AdminPanel.tsx`, and other reviewed components import icons from `lucide-react`. No design rationale for the icon style or its relationship to the KhepiLabs identity was found in the reviewed project documentation.
- **Why it matters:** A consistent icon library can be appropriate, but the skill requires icon choice to be intentional rather than an unexamined default.
- **Suggested fix:** Decide whether Lucide's stroke and shape language supports the established KhepiLabs direction. Keep relevant icons, remove decorative or generic ones, and record the rationale in the design documentation.

### 5. [LOW] Glass and blur effects are used across several surfaces
- **Rule:** R-10 (also R-12 / R-13 where applicable)
- **Evidence:** `src/admin.css` applies backdrop blur to the sticky top bar, floating elements, and modal backdrop. The public stylesheet also applies blur to search and overlay surfaces.
- **Why it matters:** Glass is intended as a limited accent (one or two elements), not a repeated surface treatment. The current usage risks flattening hierarchy.
- **Suggested fix:** After design direction is agreed, retain blur only on the surface(s) where it has a clear functional or hierarchy purpose. Prefer solid surfaces for the rest.

### 6. [LOW] Footer and section composition show template-like repetition
- **Rule:** R-05 and C-3
- **Evidence:** The public footer uses the familiar four-column Explore / Legal / Contact structure. The public information pages also share a repeated eyebrow, title, intro, and numbered-section composition.
- **Why it matters:** These structures may be valid, but the repository does not document why this exact composition serves the content better than a simpler or more varied structure.
- **Suggested fix:** Review the footer groups and page structures against actual navigation and content needs. Keep repeated structure where it improves orientation; remove or vary sections that exist only to fill a template.

## Verification limits

- This was a static repository review. I did not run the application, execute the production build, test browser interactions, or inspect real mobile viewport behavior in a browser.
- Therefore R-03, R-25, R-26, R-27, R-32, R-34, R-35, R-39, and R-40 are **not certified PASS** by this audit. In particular, contrast ratios, keyboard behavior, every interactive control, reduced-motion behavior, responsive overflow, media sizing, and runtime states still need hands-on verification.
- The project has build, lint, and format-check scripts in `package.json`; no result is claimed for them here.
- `DESIGN.md` was not present at the reviewed repository root, so no brand direction or dial values have been assumed.
